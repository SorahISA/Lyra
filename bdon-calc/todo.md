# 活動精算機：可行性與實作待辦

## 結論

可行，但這不是單純的一維背包問題。一般關卡會同時增加 pt 與 CP，活動關卡消耗 CP 並增加 pt，因此必須同時滿足：

1. 一般與活動關卡取得的 pt 總和 **恰好等於尚缺 pt**。
2. 活動關卡消耗的 CP 不得超過一般關卡產生的 CP 加上初始持有 CP。
3. 在所有可行解中，優先選擇 **總場次最少** 的解。

建議把問題建模成有界整數線性規劃（MILP），在 Web Worker 內執行。模型只有兩條主要限制式，變數是各種「隊伍 × 評級 × 倍率」打法的使用次數；相較於建立 0～30,000,000 的傳統 DP 表，MILP 不需要以目標 pt 大小配置同等規模的記憶體，也能直接處理 CP 耦合。

這類問題本質上仍是 NP-hard，因此不能承諾所有極端輸入都會瞬間完成。實作時要提供運算逾時／取消機制，並區分「已證明無解」與「時間內尚未證明」。30,000,000 pt、目前數量的隊伍與動作種類，在合理剪枝及成熟的整數規劃求解器下應屬實用範圍。

## 必須先固定的規則

### 共用資料

- 新增獨立頁面，例如 `optimizer.html`，主計算器提供「活動精算機」連結並以新分頁開啟。
- 與主計算器共用現有 localStorage 中的：
  - 目標 pt
  - 目前持有 pt
  - 一般隊伍（名稱、最高評級、pt 加成）
  - 活動隊伍（名稱、最高評級、pt 加成）
- 實際要取得的分數：`尚缺 pt = max(目標 pt - 目前持有 pt, 0)`。
- 主頁資料在另一分頁變更時，透過 `storage` 事件更新畫面，但 **不自動重算**；結果標示為「設定已變更，請重新計算」。
- 精算機自己的選項使用另一個版本化 localStorage key 保存，避免破壞現有匯入／匯出格式。

### 可使用的評級

評級順序為 `SS > S > A > B > C > D`。

- 一般隊伍可使用該隊伍最高評級及其以下的所有評級。例如最高 A 可使用 A、B、C、D。
- 活動隊伍同樣只能使用最高評級以下的評級，但第一版排除 D，因此最低為 C。
- 因此 36／20 是單一 SS 隊伍的最大動作數；最高評級較低的隊伍會有較少動作。

### 動作與整數計分

一般關卡：

| 火 | 倍率 |
|---:|---:|
| 0 | 1 |
| 1 | 5 |
| 2 | 10 |
| 3 | 15 |
| 4 | 20 |
| 5 | 25 |

活動關卡：

| 消耗 CP | 倍率 |
|---:|---:|
| 200 | 200 |
| 400 | 400 |
| 800 | 800 |
| 1,600 | 1,600 |

每一場應先算出該場完整獎勵，再向下取整。為避免 JavaScript 浮點誤差，所有基礎 pt 先以四分之一 pt 為單位儲存：

```text
單場 pt = floor(基礎 pt × 倍率 × (100 + pt 加成) / 100)

等價整數公式：
單場 pt = floor(基礎 quarterPt × 倍率 × (100 + pt 加成) / 400)
```

- 一般基礎 pt 都是整數，但仍可使用相同的 quarterPt 公式。
- 活動基礎 pt 的 `.25`／`.5`／`.75` 能以 quarterPt 精確表示。
- 隊伍加成必須是 0～500 的整數百分比；載入共用資料時也要再次驗證。
- 一般關卡取得 CP 暫定為 `評級基礎 CP × 倍率`，且不受 pt 加成影響。
- 活動 D 第一版不產生動作。

## 建議演算法

### 1. 建立動作集合

對每個一般隊伍：

1. 取得其最高評級以下的所有一般評級。
2. 為每個允許的火量／倍率建立一個動作。
3. 動作記錄：隊伍、評級、火、倍率、單場 pt、單場 CP 產量。

對每個活動隊伍：

1. 取得其最高評級以下、且不含 D 的所有活動評級。
2. 為 200／400／800／1,600 CP 建立動作。
3. 動作記錄：隊伍、評級、CP 成本、倍率、單場 pt。

安全縮減：

- 移除單場 pt 大於尚缺 pt 的動作，因為所有得分皆為非負且要求恰好命中。
- 完全相同的 `(pt, CP 變化, 火)` 動作只保留一個具名代表。
- 不可只因某動作 pt 較低就視為劣勢移除；較低得分可能是湊出精確餘數的唯一方式。

### 2. 快速判定

- 尚缺 pt 為 0：直接回報已達成，0 場。
- 某一類隊伍為空時，只停用該類動作；仍允許「純一般」或在初始 CP 足夠時的「純活動」解。
- 兩類都沒有可用動作：無解；活動動作存在但沒有足夠 CP 時，交由完整模型證明不可行。
- 計算所有單場 pt 的最大公因數 `g`；若 `尚缺 pt % g !== 0`，可立即證明無解。
- 各變數上限可設為 `floor(尚缺 pt / 該動作 pt)`，把無界問題轉成有界問題。

GCD 只是一個必要條件；通過 GCD 檢查不代表一定有可行解，仍須求解完整模型。

### 3. 整數規劃模型

令：

- `x_i`：第 i 種一般打法的次數，非負整數。
- `y_j`：第 j 種活動打法的次數，非負整數。
- `P_i`／`C_i`：一般打法的單場 pt／CP 產量。
- `Q_j`／`K_j`：活動打法的單場 pt／CP 成本。
- `T`：尚缺 pt。
- `C0`：目前持有 CP，預設 0。

限制式：

```text
Σ(P_i × x_i) + Σ(Q_j × y_j) = T
Σ(C_i × x_i) + C0 - Σ(K_j × y_j) >= 0
```

第一階段目標：

```text
minimize Σx_i + Σy_j
```

取得最少場次 `N` 後，固定 `Σx_i + Σy_j = N` 再進行第二階段 tie-break，避免用單一巨大權重造成溢位或改變第一優先目標。

求解完成後不得直接相信浮點結果；必須把每個變數四捨五入成整數，再用 JavaScript 整數重新驗證 pt 等式、CP 不等式與變數上下限。驗證失敗時視為求解器錯誤，不顯示錯誤攻略。

### 4. 執行環境與失敗狀態

- [x] 選用零依賴、Unlicense 的 `javascript-lp-solver` 1.0.3，連同授權檔放在本地，不依賴 CDN。
- [x] 將求解器放在 Web Worker，避免高難度輸入凍結頁面。
- [x] 提供取消按鈕與 20 秒時間限制。
- [x] 狀態區分：
  - 找到並驗證精確解
  - 已證明無解
  - 運算逾時／使用者取消，尚無法判定
  - 輸入或共用資料無效
- [ ] 若最終不採第三方求解器，需實作「分支限界 + LP／上界剪枝 + 模數剪枝」的精確整數求解器；不可退回 30,000,001 格乘以 CP 維度的完整 DP。

1. 先確認上方各項規則歧義，尤其是 4／5 火開關、初始 CP 與取整時點。

3. 實作動作生成、去重、GCD 預檢及結果重新驗證。

6. 完成攻略表、無解／逾時／過期狀態與響應式畫面。
7. 跑 30,000,000 pt 壓力測試，再決定是否提高目標上限。
